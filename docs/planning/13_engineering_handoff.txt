Release scope
Deliver a responsive, single-page MBTA dashboard for commuters and transit enthusiasts. Sprints 1–3 form the complete assessment. Sprint 4 may add a saved stop, direction and official departures once the core passes its checks. Sprints 5–9 cover the longer-term product. Historical collection, custom scoring and journey monitoring have no dependencies that must ship in the assessment release.

Sprint 1 — Live Map
Open on an interactive Greater Boston map on both desktop and phone. Show a title, a short description and live subway vehicle markers from the official MBTA V3 /vehicles endpoint. Use a wide desktop toolbar and a compact phone control row. Each marker must correspond to a vehicle with usable coordinates.

Sprint 2 — Vehicle details and controls
Selecting a marker shows route, direction, status and next stop where known. Distinguish “At [stop]” from “Approaching [stop]” using evidence from the feed. Show “Next stop unavailable” when the next stop cannot be established. Provide a line filter, manual refresh and last successful update time. Distinguish an empty filter result from a failed refresh. On failure, retain the last successful data and timestamp if available.

Sprint 3 — Analytics and submission
Switch between Live Map and Analytics without a full browser reload. Preserve the map’s filter on return. The chart, “Active vehicles by subway line,” compares all in-scope subway lines regardless of that filter. Combine Green branches into one bar. Verify keyboard operation and phone layout. Deploy the frontend and any backend used. Submit the fork-based PR with working deployment and screen-recording links and the completed template by November 29, 2026 at 11:59 p.m. Boston time.

Engineering design | November 24, 2026
Decisions DEC-020 to DEC-028 in 12_decision_log.txt answer the stack, hosting, refresh and freshness questions above.

Mapping library: React Leaflet, which matches both the README and the PR template checkbox and resolves D1 in 10_assessment_audit.txt.

Structure (web/src): api/ holds every MBTA request and the raw response types. domain/ holds plain, tested TypeScript: line scope and colours, normalization into a Vehicle model, stop labels, freshness rules and per-line counts. hooks/ wraps data fetching and the URL line filter. features/ holds the map, analytics and vehicle-list views. components/ holds shared controls. Raw API shapes do not pass beyond domain/normalize.ts.

Data flow:
  /vehicles?filter[route]=<in-scope routes>&include=trip,stop  (every 15 s + manual)
    -> normalize: in-scope routes only, coordinates required, one record per vehicle ID,
       stop label from current_status + included stop, direction from included trip headsign
    -> query cache: last successful data, its time, current error
       -> Live Map markers and popups (line filter applied)
       -> Analytics "Active vehicles by subway line" (no filter; Green branches combined)

Vehicle trace (live, November 24, 2026): vehicle R-548CD8D6 on route Red, current_status STOPPED_AT, stop "JFK/UMass", trip headsign "Alewife". Marker on the Red layer; popup "At JFK/UMass, toward Alewife"; adds 1 to the Red bar. Included trip and stop records resolve direction and next stop with no further requests.

Live-data observations (November 24, 2026): anonymous limit 20 requests/min per IP; streaming returns 406 without a key; 1 of 108 subway vehicles had no stop; update ages p50 19 s, p90 55 s, max about 7 min, with every update older than 90 s belonging to a train at a terminal.

Still to verify against live data: Green Line next-stop accuracy on surface branches; whether HTTP 304 responses count against the rate limit; vehicle counts during service changes and late at night.
