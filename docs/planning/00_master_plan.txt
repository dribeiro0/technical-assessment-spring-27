1. WHAT ENROUTE IS
======================================================================

Working tagline [PROPOSED]: "Know the T before you go."

EnRoute is a real-time Boston transit product built on the official
MBTA V3 API. It is meant to answer four questions [ACCEPTED as product
direction]:

  1. How is the MBTA performing right now?
  2. Where are the trains and buses?
  3. What disruptions should I know about?
  4. How will this affect my commute?

The difference from an ordinary MBTA dashboard is interpretation. An
ordinary tracker answers "where is my train and when will it arrive?"
EnRoute also tries to answer "how reliable is my journey, what is
going wrong, how does it affect me, and what should I do?" [ACCEPTED as
the guiding distinction]

It serves two audiences through one shared set of facts [ACCEPTED]:
  - everyday commuters deciding whether and when to travel
  - transit enthusiasts exploring how the network is behaving

3. DELIVERY ORDER
======================================================================

The deadline is Sunday, November 29, 2026, 11:59 p.m. Boston time. The
assessment is the first gate. "Core to the product" and "mandatory for
the assessment" are different lists, and the second one comes first.

SPRINT ROADMAP [PROPOSED] | Baseline 0.1
Assessment IDs refer to the release criteria in file 10.

1. App shell and live map | R2, R3, R4
   The responsive landing view shows the title, description and an interactive
   Greater Boston map. Each in-scope vehicle with usable coordinates
   appears at the position associated with its source ID.

2. Vehicle details and controls | R5, R6, R7
   Add marker popups with route, direction, status and next stop when
   available. Add a line filter, manual refresh and last-updated time.
   Refresh preserves the selected line. Missing next-stop data has an explicit unavailable state.

3. Analytics, polish and submission | R1, R8, R9, R10; recheck R2
   Add an Analytics view with vehicle counts grouped by subway line.
   Use one page with shared selection across views. Finish responsive
   styling and keyboard access. Deploy the frontend and any backend.
   Map and chart use consistent route identities. Switching views preserves the line selection without reloading the document. Release requires R1-R10 in file 10.

4. Basic My Commute | optional assessment stretch
   Save one stop and direction on the device and show official upcoming
   departures. Label any timetable fallback. Offer the saved commute
   on either device, with a commute-first phone view for return visits.
   Saved preferences survive a reload. Departures carry their source and update time.

5. Service alerts and overview | personal app
   Add the network overview, official alerts and journey relevance.
   Alert relevance follows the affected journey segment. Detected irregularities follow in Sprint 7.

6. Continuous collection and public trends | personal app
   Collect service observations independently of visits; record gaps.
   Recorded gaps remain distinct from observed periods with no service.

7. Transit Intelligence and experimental scoring | personal app
   Compare expected and observed service; evaluate prediction accuracy.
   Keep validation separate from public analytics. Introduce network,
   route and commute scores only where the evidence supports them.
   Each score includes contributing evidence; insufficient observations yield an unknown state.

8. Active journey monitoring | personal app
   Confirm boarding, follow onboard progress and offer destination alerts
   when trip identity, data freshness and rider settings support them.
   Loss of reliable stop progress suppresses the approaching-destination alert.

9. Expansion beyond subway | personal app
   Extend validated features mode by mode. Check service patterns and
   coverage before reusing any reliability measure.
   Existing subway behavior remains a release criterion for each additional mode.

5. WHAT GETS DEFERRED IF THE DEADLINE IS AT RISK
======================================================================

Sprint 3 covers the complete assessment. Sprint 4 is optional once the core
meets its release criteria and the submission deadline is secure. Route
overlays and streaming remain optional and unscheduled.

ACCEPTED RELEASE BEHAVIOR
- Sprint 1: Live Map opens on desktop and phone. Use a desktop toolbar
  and a compact phone control row. Sprint 2 adds filter and refresh.
- Sprint 2: use "At [stop]" or "Approaching [stop]" when supported.
  Show "Next stop unavailable" if a reliable next stop cannot be identified.
- Sprint 2: distinguish an empty successful filter result from a failed
  refresh. Keep the last successful data and timestamp on refresh failure.
- Sprint 3: the map remembers its line selection across view changes.
  "Active vehicles by subway line" compares all in-scope subway lines
  independently of the map filter. Combine Green branches into one bar.
- Sprint 4 (optional): returning phone users with a saved commute may
  start on departures. My Commute remains accessible on desktop.
