DEC-001  Chaos Meter is a transit intelligence product, not a dashboard
----------------------------------------------------------------------
Status:       ACCEPTED
Decision:     Interpret MBTA data into actionable answers (how is the T,
              where are vehicles, what is disrupted, how does it affect
              me) instead of only displaying it.
Alternatives: A data dashboard meeting the assessment checklist only.
Rationale:    An actual product someone in Boston would use before
              leaving the house, not another MBTA data dashboard. This
              is the assistant's wording in its opening reply, which
              restated decisions from earlier context not in the share.
Consequences: Scoring, relevance, and journey features exist; more work
              than the assessment needs, hence 00's delivery order.
Anchor:       Opening table "What we've already decided": hybrid
              platform; My Commute high-priority; landing system
              overview.

----------------------------------------------------------------------
DEC-002  Two audiences
----------------------------------------------------------------------
Status:       ACCEPTED
Decision:     Everyday commuters and transit enthusiasts, both primary.
Consequences: Two emphases (DEC-003); both need the same facts.
Anchor:       Opening table "Primary audience".

----------------------------------------------------------------------
DEC-003  One data system, two switchable experiences; overview landing
----------------------------------------------------------------------
Status:       ACCEPTED
Decision:     Command Center emphasized on desktop, Commuter Companion on
              mobile, either reachable manually on any device, same
              facts underneath. Desktop lands on the network overview;
              mobile Home leads with the personal commute and keeps a
              compact network status.
Alternatives: One responsive layout compressed for phones.
Rationale:    Exploring the network and catching a train are different
              tasks. Desktop "for exploring"; mobile "for making
              decisions on the go" (assistant, agreed).
Consequences: Shared components; view state must not diverge by mode.
Resolved:     The planning conversation's navigation diagram ("Desktop
              default: Network Overview / Mobile default: Commute
              Home") and David's master prompt agree on this split.
Anchor:       David: "We have a different mobile view option so that
              when they're on their phone trying to take a look and
              track the train, it's a more convenient view."
              Manual switching was proposed by the assistant, listed in
              "Decisions we're keeping", and reaffirmed in David's
              baseline instructions.

DEC-005  Whole-network architecture, subway proven first
----------------------------------------------------------------------
Status:       ACCEPTED (strategy); PROPOSED (bus -> CR -> ferry order)
Decision:     Model all MBTA modes; make Red, Orange, Blue, Green work
              end to end before expanding.
Alternatives: Subway only (easier, small audience); subway + bus; entire
              MBTA at once (different reliability models, complexity).
Rationale:    Ambition without sacrificing quality.
Consequences: Generic entity model; mode-specific scoring expectations.
Anchor:       David: "I agree. Let's support the entire MBA network
              architecturally and make sure that Subway works perfectly,
              and then we transition to the entire MBA MBTA once
              everything else is flushed out. What do you think?"

----------------------------------------------------------------------
DEC-006  Chaos Score: research-backed, versioned, weights not locked
----------------------------------------------------------------------
Status:       ACCEPTED (approach); PROPOSED (every weight); UNVALIDATED
              (research basis for weights)
Decision:     Score passenger impact, not counts. Calibrate against
              evidence before fixing weights. Ship as experimental.
History:      A (illustrative simulator: severity 35, coverage 20,
              delays 25, suspensions 20) -> B (five pillars: disruptions
              30, schedule deviation 25, frequency 20, coverage 15,
              availability 10) -> C (excess waiting 30, disruptions 25,
              excess travel time 20, unpredictability 15, availability
              10; coverage as exposure modifier). See 03.
Rationale:    David asked for research-based weights instead of
              intuition. C aligns with time-lost measures (MBTA ETT,
              Furth & Muller).
Consequences: Needs continuous history (DEC-012) to calibrate; needs a
              confidence model and missing-data rules.
Open:         Final weights; suspension floor; "enough evidence"
              threshold; headway threshold for switching wait models;
              band labels (A's "Moderate" at 27 vs bands' "Minor").
Anchor:       David: "What do you think chaos should be determined by?"
              and "We can probably use the weights in comparison to
              real research and to create a more accurate result,
              right?" Roadmap then: "Direction decided".

DEC-008  Official MBTA predictions first
----------------------------------------------------------------------
Status:       ACCEPTED
Decision:     Show official predictions; fall back to clearly labelled
              scheduled times; evaluate prediction reliability; no
              custom arrival algorithm unless evidence justifies one.
Alternatives: Independent predictions; hybrid with own fallbacks (the
              assistant's first recommendation).
Rationale:    MBTA has operational data we lack; lower risk of
              misleading riders; lower complexity.
Consequences: Differentiation comes from evaluating predictions, not
              replacing them.
Anchor:       David: "Why would we do a hybrid approach over just using
              the MBTA predictions?" then "That sounds good."

----------------------------------------------------------------------
DEC-009  Expected vs observed intelligence (hybrid alerts)
----------------------------------------------------------------------
Status:       ACCEPTED
Decision:     Combine official notices with our own detected
              irregularities, origins kept distinct; lifecycle includes
              recovery; correlated evidence counted once.
Consequences: Needs schedules + observed service + history.
Anchor:       David: "Pairing it with the brainstorm about us creating
              our own predictions, because the robot's given to us and
              what we find changes, right?" then "I agree."
