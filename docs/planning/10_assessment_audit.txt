1. CORE REQUIREMENTS MATRIX
======================================================================

R1  Single-page app, no full reloads when switching views [Sprint 3]
    Source: README core #1 (examples: Live Map, Service Alerts & Table,
            Line Analytics); template "Built as a SPA".
    Planned: client-side navigation between Live Map and Analytics.
    Depends: none.
    Check: switch every view; browser shows no document reload
           (network panel: no new document request); state such as
           filters survives the switch.
    Evidence: recording segment clicking through all views.
    Status: NOT STARTED

R2  Polished, responsive UI with catchy title and apt description [Sprint 1; recheck in Sprint 3]
    Source: README core #2 (also "cool fonts"; MBTA palette and subtle
            motion "strongly encouraged"); template "beautiful frontend
            ... catchy title, apt description, cool fonts/colors ...
            any screen size".
    Planned: one responsive map and chart interface on desktop and phone.
             Title "Chaos Meter"; description [OPEN]. Visual identity
             [DEFERRED] but must be decided before submission.
    Depends: responsive app shell.
    Check: usable at phone (~375 px), tablet, desktop widths; title and
           one-line description visible on landing.
    Evidence: recording at desktop and narrow width; screenshots.
    Status: NOT STARTED

R3  Real MBTA V3 data [Sprint 1]
    Source: README core #4 ("Successfully fetch and render live data");
            template "fetches and renders data from an external MBTA
            API".
    Planned: shared retrieval layer (02).
    Check: values on screen match a direct API response at the same
           time; no mock data in production.
    Evidence: recording with the network panel or a timestamp.
    Status: NOT STARTED

R4  Interactive map centred on Greater Boston with live /vehicles [Sprint 1]
    markers
    Source: README core #3; template "Uses React Leaflet to render an
            interactive map".
    Planned: Live Map (04, 11).
    Depends: R3, route reference data.
    Check: map opens centred on Greater Boston; pan/zoom work; marker
           count equals vehicles with positions in the current response
           (after filters).
    Evidence: recording.
    Status: NOT STARTED

R5  Clicking a marker opens a popup: route, direction, current status, [Sprint 2]
    next stop
    Source: README core #3 ("such as its route, direction, current
            status, and next stop"). Not in the template checklist.
    Planned: vehicle details (04 section 1).
    Depends: R4; vehicle -> trip -> stop sequence -> stop.
    Check: popup shows all four; next stop says "unavailable" when the
           data is missing; values match /vehicles for that id.
    Evidence: recording of at least two vehicles on different lines.
    Status: NOT STARTED

R6  Search bar or filter controls [Sprint 2]
    Source: README core #4 (by line, route, or stop name). Not in the
            template checklist.
    Planned: one line filter on the live map.
    Check: choosing "Red" leaves only Red vehicles; clearing it restores all lines in scope.
    Evidence: recording.
    Status: NOT STARTED

R7  Manual refresh button or auto-refresh toggle [Sprint 2]
    Source: README core #4. Not in the template checklist.
    Planned: a manual refresh button and last successful update time.
    Note: background or continuous collection does not satisfy this

    Check: manual refresh requests current data and preserves the line filter.
           A failed request leaves the previous success time visible.
    Evidence: recording.
    Status: NOT STARTED

R8  At least one chart from API data [Sprint 3]
    Source: README core #5 (Chart.js, Recharts, D3 given as examples);

    Planned: active vehicles by line, live, with scope, unit, update
             time (07 section 2). Vehicle counts are not a chaos score.
    Check: chart values match a count of the current /vehicles response.
    Evidence: recording.
    Status: NOT STARTED

======================================================================

  D1  Mapping library: README says "React Leaflet (or a similar mapping
      library)"; the template checkbox says "Uses React Leaflet". The
      engineering choice stays open. If another library is used, the
      PR should say so next to that checkbox.
  D2  The template's short checklist omits details the README still
      requires: search/filters (R6), refresh control (R7), live markers
      from /vehicles (R4), and popup fields (R5). Build to the README.
  D3  README asks for "cool fonts"; template asks for "cool
      fonts/colors". Same intent; visual identity still [DEFERRED].
  D4  Deployment: README "frontend (and backend, if applicable)";
      template only "Deployed the frontend".

7. RISKS
======================================================================

  - Scope: the product plan is far larger than five days allows.
    Mitigation: 00 delivery order and cut list.
  - Deployment unknowns: hosting choice and any backend or collector
    are not decided. Deploy something early.
  - Map library vs template wording (D1).
  - Data gaps: next stop or predictions missing for some vehicles.
    Popups must show "unavailable" instead of failing.
  - Rate limits without an API key.
  - Recording and PR left too late: budget time before the deadline.
